# Feature Specification: 跨 Chunk 材质合批

**Feature Branch**: `001-cross-chunk-batching`
**Created**: 2026-04-12
**Status**: Draft
**Input**: User description: "相邻 Chunk 的相同纹理方块无法共享 InstancedMesh，进行跨 Chunk 材质合批优化，将相邻 chunk 的相同纹理合并，并提供轻量验证方法"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 跨 Chunk 相同纹理合批渲染 (Priority: P1)

玩家在游戏世界中移动，视野内同时加载了多个相邻区块。系统自动将相邻区块中相同纹理的方块合并到同一个渲染批次中，减少 GPU 绘制调用次数。玩家感知到游戏帧率更平滑，尤其在区块加载密集时卡顿明显减少。

**Why this priority**: 这是本功能的核心价值——通过减少 draw call 提升渲染性能。没有这一步，后续优化和验证都无从谈起。

**Independent Test**: 在浏览器控制台输入验证命令，查看合批前后的 draw call 数量对比，以及每个合批组包含的区块列表和实例数量。

**Acceptance Scenarios**:

1. **Given** 多个相邻区块已加载完成，**When** 系统执行渲染，**Then** 相同纹理的方块跨区块合并为同一个渲染批次，draw call 数量低于合批前
2. **Given** 玩家在区块边界放置或移除方块，**When** 操作完成后，**Then** 受影响的合批组在下一帧自动更新，渲染结果正确显示变更
3. **Given** 玩家移动导致新区块加载或远区块卸载，**When** 区块集合发生变化，**Then** 合批组自动重建，无内存泄漏

---

### User Story 2 - 轻量验证方法 (Priority: P2)

开发者（或玩家）在游戏运行中通过浏览器控制台输入简单命令，即时查看当前跨 Chunk 合批的统计数据，包括：总 draw call 数、每个纹理组的合并区块数、实例总数。

**Why this priority**: 验证方法是确认优化效果和排查问题的关键工具，必须在核心合批功能完成后立即可用。

**Independent Test**: 在游戏运行时打开控制台，输入指定命令，确认输出包含合批统计数据且数值合理。

**Acceptance Scenarios**:

1. **Given** 游戏已运行且多个区块已加载，**When** 在控制台输入验证命令，**Then** 输出包含：总 draw call 数、各纹理组的区块合并数、实例总数
2. **Given** 游戏刚启动仅加载少量区块，**When** 输入验证命令，**Then** 数据准确反映当前状态，不会报错

---

### User Story 3 - 区块动态更新时合批保持一致 (Priority: P3)

玩家挖掘或放置方块后，受影响区块所在的合批组及时更新，确保画面显示与实际方块状态一致，不出现残影、丢失或闪烁。

**Why this priority**: 正确性是优化的底线——如果合批导致渲染错误，性能提升毫无意义。作为独立质量保障场景单独列出。

**Independent Test**: 在区块边界连续快速放置和移除方块，观察画面是否与操作一致、无闪烁或延迟。

**Acceptance Scenarios**:

1. **Given** 两个相邻区块已合批渲染，**When** 在其中一个区块边界处放置方块，**Then** 方块立即正确显示，合批组自动更新
2. **Given** 一个合批组覆盖 4 个区块，**When** 对其中一个区块执行大规模操作（如 TNT 爆炸），**Then** 所有受影响方块正确更新，合批组在操作完成后重建

### Edge Cases

- 当一个区块正在合批中而另一个相邻区块被卸载时，系统如何处理？→ 合批组需要支持增量更新，卸载时移除对应区块的数据并重新组装实例矩阵
- 当所有可见区块仅有一种纹理的方块时，是否仍创建合批组？→ 是，单区块也应纳入合批系统以保持逻辑一致
- 当玩家视距切换（如从 2 区块切换到 3 区块）时，合批组如何响应？→ 触发全局合批重建

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 将视野内相邻区块中相同纹理的方块合并到同一个渲染批次中，减少每帧绘制调用次数
- **FR-002**: 合批 MUST 基于纹理（材质）分组，同一纹理的所有可见方块无论属于哪个区块都合并到同一批次
- **FR-003**: 系统 MUST 在区块加载、卸载或方块变更时自动更新受影响的合批组，保持渲染结果与实际方块状态一致
- **FR-004**: 系统 MUST 提供轻量级控制台验证命令，展示当前合批统计数据（总 draw call 数、各纹理组的区块合并数和实例总数）
- **FR-005**: 合批更新 MUST 在同帧或下一帧内完成，不造成可感知的卡顿（单帧耗时增加不超过 5ms）
- **FR-006**: 系统 MUST 在区块卸载时正确释放该区块在合批组中占用的资源，无内存泄漏
- **FR-007**: 现有的方块操作（挖掘、放置、爆炸）MUST 在合批模式下行为不变，不引入渲染错误

### Key Entities

- **合批组（Batch Group）**: 按纹理分组的渲染批次，包含来自多个区块的同类方块实例，维护统一的实例矩阵集合
- **区块合批数据（Chunk Batch Data）**: 每个区块在合批系统中的数据快照，记录该区块中各纹理的方块实例信息（位置、AO、法线等）
- **合批管理器（Batch Manager）**: 全局协调器，管理所有合批组的创建、更新、销毁，响应区块生命周期事件

## Assumptions

- 渲染距离内通常有 25-49 个区块（视距 2-3），每个区块有 5-15 种纹理，合批前约有 125-735 个 draw call
- MaterialManager 已支持纹理分组机制，可复用现有材质索引映射
- 现有的面剔除和 AO 计算结果仍按区块独立产出，合批层仅负责将结果组装到统一的实例矩阵中
- 合批是纯渲染层优化，不改变区块数据结构或 Worker 通信协议

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在标准视距（3 区块，约 49 个区块加载）下，draw call 数量相比合批前减少 60% 以上
- **SC-002**: 合批系统启用后，平均帧率不低于合批前的水平（不引入性能回退）
- **SC-003**: 通过验证命令可在 100ms 内获得完整的合批统计输出
- **SC-004**: 连续进行 50 次方块放置/移除操作，画面渲染无错误（无残影、丢失、闪烁）
- **SC-005**: 区块加载/卸载时无内存泄漏（通过控制台内存快照对比验证）
