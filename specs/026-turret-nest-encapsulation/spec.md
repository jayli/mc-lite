# Feature Specification: 炮塔与丧尸巢穴实体封装重构

**Feature Branch**: `026-turret-nest-encapsulation`
**Created**: 2026-03-21
**Status**: Draft
**Input**: User description: "炮塔和丧尸巢穴除了方块构成之外，还有与之伴随的其他立体形状、以及交互功能。如何进一步优化炮塔和丧尸巢穴这类携带额外立体形状和交互功能的对象，让他们能很好的跟主世界互动，而且可以很好的被持久化。我想对炮塔和丧尸巢穴做更好的封装，以更好的集中管理这类携带其他形状和携带交互的这类实体。现在炮塔和丧尸巢穴的单独处理的逻辑散落在worker，chunk，player 以及持久化保存中，都有特殊处理的逻辑存在，这样非常不方便维护，所以我想对炮塔和丧尸做进一步的封装，降低在各个模块中的耦合深度。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 统一实体生命周期管理 (Priority: P1)

作为游戏开发者，我需要统一的管理接口来创建、更新和销毁炮塔和丧尸巢穴，而不是在多个模块中分散处理。这样可以降低代码重复，减少维护成本。

**Why this priority**: 当前逻辑散落在多个模块中，导致添加新功能或修复bug时需要修改多处代码，容易遗漏和引入新问题。

**Independent Test**: 可以通过创建一个炮塔或丧尸巢穴，验证所有相关组件（方块、附加形状、交互功能）是否通过单一入口正确初始化。

**Acceptance Scenarios**:

1. **Given** 游戏世界已加载，**When** 在指定位置创建一个炮塔实体，**Then** 应该自动完成方块放置、附加形状渲染、交互功能绑定，无需调用者分别处理
2. **Given** 世界中存在一个炮塔，**When** 调用统一销毁接口，**Then** 方块、形状、交互状态应该一并清理，不会出现残留

---

### User Story 2 - 透明的持久化支持 (Priority: P1)

作为玩家，我期望游戏保存和加载时，炮塔和丧尸巢穴的状态（位置、方向、交互状态）能够正确恢复，无需重新手动放置。

**Why this priority**: 持久化是游戏体验的基础，当前分散的逻辑导致保存/加载容易出错。

**Independent Test**: 可以通过保存游戏、退出、重新加载的流程，验证炮塔和丧尸巢穴的状态是否正确恢复。

**Acceptance Scenarios**:

1. **Given** 世界中存在多个炮塔和丧尸巢穴，**When** 玩家保存游戏并重新加载，**Then** 所有实体应该恢复到保存时的位置和状态
2. **Given** 炮塔正在执行某个动作（如瞄准），**When** 保存并加载游戏，**Then** 炮塔应该继续执行或回到合理状态

---

### User Story 3 - 与世界的无缝交互 (Priority: P2)

作为玩家，我可以通过统一的方式与炮塔和丧尸巢穴交互（如点击、触发），而不需要关心它们内部由多少部分组成。

**Why this priority**: 统一交互接口可以提升玩家体验，并简化新实体类型的添加。

**Independent Test**: 可以通过玩家点击炮塔或丧尸巢穴，验证交互事件是否正确触发并路由到对应的处理逻辑。

**Acceptance Scenarios**:

1. **Given** 玩家靠近炮塔，**When** 点击炮塔的任何可见部分，**Then** 应该触发统一的交互事件
2. **Given** 玩家与丧尸巢穴交互，**When** 执行特定操作，**Then** 巢穴应该响应并反馈状态变化

---

### User Story 4 - 模块间低耦合 (Priority: P2)

作为开发者，我可以独立修改炮塔或丧尸巢穴的内部实现，而不需要同时修改 World、Chunk、Player 或 Worker 等模块的代码。

**Why this priority**: 降低耦合是这次重构的核心目标，有助于未来的功能扩展和维护。

**Independent Test**: 可以修改实体的内部实现细节，验证其他模块无需同步修改。

**Acceptance Scenarios**:

1. **Given** 炮塔的内部渲染逻辑需要调整，**When** 只修改实体模块内的代码，**Then** Chunk 和 Engine 模块应该无需修改
2. **Given** 添加新的实体类型（如陷阱），**When** 遵循统一封装接口，**Then** 可以在不修改现有模块的情况下集成到世界

---

### Edge Cases

- 当区块被卸载时，实体状态如何保存和恢复？
- 当实体部分方块被玩家破坏时，如何处理？
- 当持久化数据版本不兼容时，如何优雅降级？
- 多个实体在同一位置附近时，交互优先级如何确定？

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须提供统一的实体管理器（EntityManager），负责所有复杂实体（炮塔、丧尸巢穴等）的生命周期管理
- **FR-002**: 实体必须封装自身的方块组成、附加形状渲染和交互功能，对外暴露简洁的创建/更新/销毁接口
- **FR-003**: 系统必须支持实体的序列化和反序列化，确保保存/加载时状态完整恢复
- **FR-004**: World 模块必须通过 EntityManager 间接操作实体，禁止直接访问实体的内部状态
- **FR-005**: Chunk 模块只负责方块层面的渲染，实体的视觉表现由实体自身管理
- **FR-006**: Player 模块通过统一接口与实体交互，无需了解实体的具体组成
- **FR-007**: Worker 进程只处理方块数据层面的计算，实体逻辑在主线程通过 EntityManager 处理
- **FR-008**: 实体必须定义明确的边界，当方块被破坏时实体应该知道并作出响应
- **FR-009**: 系统必须支持实体类型的注册机制，新实体类型可以通过注册而非修改现有代码来添加

### Key Entities *(include if feature involves data)*

- **ComplexEntity**: 复杂实体基类，定义所有复杂实体的通用接口（create/update/destroy/serialize/deserialize）
- **TurretEntity**: 炮塔实体，包含方块组成、炮管模型、瞄准逻辑、射击功能
- **ZombieNestEntity**: 丧尸巢穴实体，包含方块组成、生成逻辑、生命值管理
- **EntityManager**: 实体管理器，管理所有活跃实体，提供查询和操作接口
- **EntityPersistence**: 实体持久化接口，负责序列化和存储实体数据
- **EntityRenderer**: 实体渲染器，负责实体附加形状的渲染
- **EntityInteraction**: 实体交互接口，定义实体与玩家交互的方式

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 添加新类型实体时，需要修改的文件数量从当前的5个以上减少到2个以内（Entity 定义 + 注册）
- **SC-002**: 实体的保存/加载成功率达到100%，加载后的实体状态与保存前完全一致
- **SC-003**: World、Chunk、Player、Worker 模块中移除所有与炮塔/丧尸巢穴相关的特殊处理代码
- **SC-004**: 实体的交互响应延迟保持在50ms以内
- **SC-005**: 代码耦合度指标：实体模块与其他模块的依赖关系从当前的分散耦合变为单一接口依赖
- **SC-006**: 新实体类型的集成时间从当前的数小时减少到30分钟以内

## Assumptions

- 实体主要以方块形式存在于世界中，附加形状用于视觉增强
- 实体的交互功能以触发器/回调形式实现
- 持久化采用 JSON 格式，支持版本控制
- 主线程负责实体逻辑，Worker 只处理纯方块计算
