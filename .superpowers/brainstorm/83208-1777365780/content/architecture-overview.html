第二阶段架构概览

从一阶段到二阶段：特殊实体跨重启持久化改造

一阶段回顾（已完成）

解决了单次 runtime 会话内 chunk 卸载/重载的正确性问题，通过 cache 快照桥接层实现了：

  • Chunk 卸载前同步快照 blockData
  • cache 优先读取优先级
  • 特殊实体快照增强（id 去重）

第二阶段目标

将特殊实体正式迁入 worldStore / IndexedDB，实现跨页面重启的持久化恢复。

// 当前 cache.entities 结构
{
  "turrets": [...],
  "zombieNests": [...],
  "minecarts": [...]
}
// 仅存在于内存
// 页面关闭即丢失

1. 评估 cache.entities 迁入 worldStore

扩展 ChunkRecord 格式，runtime entities 纳入 worldStore 统一管理

// 设想的 Repository 抽象
RuntimeEntityRepository {
  getEntities(chunkKey, type)
  saveEntity(chunkKey, entity)
  removeEntity(chunkKey, id)
  flushToStore(chunkKey)
}
// 统一三个 manager 的读写

2. 设计 RuntimeEntityRepository

统一炮塔/巢穴/矿车的快照读写抽象，消除重复逻辑

// chunk 级生命周期
chunk.activate()   → 实体加载、启动逻辑
chunk.deactivate() → 实体停用、写入快照

// 当前：manager 全局持有
// 目标：显式生命周期

3. chunk 级 activate/deactivate

显式生命周期管理，评估性能收益与复杂度

关键决策点

统一路径的好处

  • 手动存档和自动持久化合并为单一路径
  • 特殊实体纳入 worldDeltas
  • 跨重启恢复成为可能

需要解决的问题

  • ChunkRecord 格式扩展（向后兼容）
  • worker 序列化协议变更
  • 迁移现有存档数据
