方案 A 设计：影响分析

第 3/3 节：影响范围、兼容性、风险

修改文件清单

文件 变更类型 说明

向后兼容性

兼容性保障

  • ChunkRecord.runtimeEntities 是可选字段，旧存档不含此字段
  • Chunk.loadFromRecord 回退到 cache.entities 读取旧格式
  • ensureChunkEntitiesMigrated 在读取时自动迁移，无需手动操作
  • world_deltas 表在迁移后保留（不删除），仅作为降级保护
  • 手动存档加载兼容新旧两种 worldDeltas 格式

潜在风险

  • collectSnapshot 改为从 worldStore 读取，但只有已加载 chunk 会被序列化——未加载区域不会进入存档。这需要在 UI 中提示用户"当前存档仅包含已探索区域"
  • 三个 manager 仍持有全局实体引用，长时间运行可能积累内存（但这与一阶段行为一致）

明确不做的事

  • RuntimeEntityRepository 抽象层（独立职责拆分，留待后续）
  • chunk activate/deactivate 生命周期钩子
  • world_deltas 表的彻底删除（保留作为降级保护）
  • Worker 端 entity 处理（entities 始终在主线程收集和写入）
  • Region 级 entity 聚合（保持 chunk 级粒度）

验证策略

  • 回归测试：放置炮塔/巢穴/矿车 → 跑远卸载 → 返回确认恢复
  • 跨重启测试：放置实体 → 关闭页面 → 重新打开 → 确认实体存在
  • 手动存档测试：存档 → 清除 world_deltas → 加载 → 确认实体正确恢复
  • 渐进迁移测试：加载旧存档 → 读取包含实体的 chunk → 确认 runtimeEntities 已回填
